# per_block 01 — one scale per 32x32 tile

Read the [kernel overview](README.md) for the accuracy trade-off and the
lane-width rule, and [per_token/01](../per_token/01_raw_fp32sf.md) for the
three-pass reduce/scale/apply structure. What is new here is that the reduction is
two-dimensional.

## Worked example

A `(32, 64)` tensor is two 32x32 tiles. Put the maximum in different rows:

| | |
|---|---|
| `x[0, 0] = 4.0` | tile (0,0) |
| `x[31, 1] = 2.0` | same tile, 31 rows away |
| `x[0, 32] = 1.0` | tile (0,1), its own smaller maximum |
| `sf[0, 0]` | `4.0/448` |
| `q[0, 0]` | `448` — the maximum lands on the limit |
| `q[31, 1]` | `224` — scaled by the *same* tile scale |

The reduction spans all 32 rows, not just one. That is the whole difference from
`per_token`.

## The tile is flattened, and reduced 64 lanes at a time

A 32x32 bfloat16 tile is 1024 values. Its rows are not contiguous in global memory
(stride $K$), so the DMA brings the tile into a UB buffer of shape `(32, 32)` —
which *is* contiguous — and the vector code then treats it as one flat run:

```python
flat = T.Tensor((BM * BK,), T.bfloat16, x_ub.data)   # a view, no copy
```

Reducing 1024 values 64 at a time takes 16 steps. Each step's maximum goes to a
scratch buffer, and a final reduction over those 16 values gives the tile maximum.
That two-level shape — reduce within a register, then reduce the partials through
UB — is how any cross-register reduction is written here.

## The accumulator must be a register array

The partial-maxima approach above avoids the issue, but the obvious alternative —
keeping a running maximum in a register across the loop — runs into a frontend
rule worth knowing: **SIMD values are immutable**.

```python
acc = V.vmax(acc, V.vabs(v, mask), mask)      # Immutable variable `acc` is used
                                               # outside its defining region
```

It has to live in a register array — `S.alloc_local((1,), T.float32)` or
`V.alloc_local((1,), V.vreg(128, T.float32))`. The error message does not say that,
which is why it is recorded in [known issues](../../known-issues.md).

## PTO vs ASC — the reduction loop is half as long

ASC's widening load produces 64 float32 lanes, so a 1024-value tile is 16
reduction steps. VMI has a 128-lane logical float32, and one convert reaches it:

```python
ASC: S.vcvt(S.vld(flat[c], dist="UNPK_B16"), T.float32)   ->  64 lanes
PTO: V.vcvt(V.vload(flat[c], size=128), "float32")        -> 128 lanes
```

So the same work is 8 steps rather than 16, and the partial-maxima buffer is half
the size. ASC *could* process 128 channels per iteration, but only by issuing two
loads and two reduces and tracking two registers by hand — which is exactly what
`per_token`'s ASC files do.

**But the static operation count does not show this.** `tools/vf_lines.py` reports
21 for ASC against 22 for PTO on this variant: VMI needs explicit `size=` and mask
operands, and a whole-vector `group=1` reduce gives it nothing to factor out. The
saving is in iterations executed, not operations written. Both numbers are in the
[kernel overview](README.md); neither alone is the answer.

## GPU vs NPU

The CUDA version uses 256 threads and `T.reduce_absmax` over a reshaped fragment;
a two-dimensional reduction is no harder for it than a one-dimensional one, because
a fragment's shape is just an index space. Here the shape decides whether the
kernel compiles at all — see the lane-width discussion in the overview.

## SIMT — the same two levels, for the same reason

One scale for 1024 values means reducing all the way to a scalar, and no vector
style escapes doing it in two levels: a vector reduction stops at one value per
register, so partials have to meet in UB. SIMT's version is the GPU idiom and has
exactly the same shape — a partial per thread into shared, then one thread
finishing:

```python
for t in T.Parallel(bm):                       # level 1: one thread per row
    amax = T.alloc_var(T.float32); amax = E4M3_CLAMP_MIN
    for j in T.serial(bk):
        amax = T.max(amax, T.abs(T.Cast("float32", x_ub[t, j])))
    row_ub[t] = amax

for _z in T.Parallel(1):                       # level 2: fold the partials
    tile = T.alloc_var(T.float32); tile = E4M3_CLAMP_MIN
    for t in T.serial(bm):
        tile = T.max(tile, row_ub[t])
    sf_ub[0] = tile / E4M3_MAX
    inv_ub[0] = E4M3_MAX / tile

for i, j in T.Parallel(bm, bk):                # apply: one shared scalar
    q_l[i, j] = T.Cast("float32", x_ub[i, j]) * inv_ub[0]
```

18 lines against ASC's 21 and PTO's 25 — a 3-line gap, among the narrowest in the
ladder (only [`cast_back/04`](../cast_back/04_per_channel_sf.md), at zero, is
narrower), and the honest reading is that **SIMT buys nothing here**. There is no
index arithmetic to simplify: the tile *is* the reduction domain, so none of the
three tiers has to compute which value belongs to which scale.

Two small notes. The 2-D UB tile is correct in this kernel, unlike
[per_token/01](../per_token/01_raw_fp32sf.md) — the tile really is 32 tokens by
32 channels, so `T.copy`'s 2-D region is exactly what is wanted. And a scalar
result belongs in a one-element **shared** buffer rather than a fragment, so that
every thread in the apply pass can read it.

## What the harness checks

- divisibility guards on both $M$ and $K$, with messages;
- scales within 1 ULP on the NPU tiers, exact on the torch tier;
- FP8 values via `assert_fp8_near`;
- the torch tier also runs `(64, 64)`, which has two tile *rows*, so an
  implementation that collapsed the row term would pass at `(32, 128)` and fail
  there.
