# per_block 03 — FP4 (e2m1) output on a 32x32 tile

`quant_max` becomes 6.0 and the values pack two per byte. The conversion path is
the one established in [per_token/04](../per_token/04_fp32_in_fp4_out.md): there is
no float32-to-e2m1 instruction, so it goes `float32 -> bfloat16 (round to odd)
-> e2m1`. Read that page for why the intermediate must be rounded to odd.

## The tile makes the pairing natural

`per_token/04` had to pair up two 64-lane registers to feed `S.vdintlv`. Here the
tile is already a flat 1024-value run, so the two halves of each 128-value chunk
are simply adjacent — the pairing is an artefact of the data layout rather than
something the kernel has to arrange.

A small thing, but it is the sort of reason production has a separate code path per
granularity: the same arithmetic wants a different loop shape depending on how the
data happens to be laid out in UB.

## The accuracy interaction

One scale over 1024 values *and* one mantissa bit is the ladder's coarsest
combination, and it is the clearest demonstration that granularity and format
interact rather than adding up:

Round-trip error, mean over 8 seeds at `(64, 256)`:

| | e4m3 | e2m1 |
|---|---|---|
| per_token (32 values/scale) | 2.9% | 12.6% |
| per_block (1024 values/scale) | 3.5% | 15.0% |

The granularity gap is 0.6 points at e4m3 and 2.4 points at e2m1 — about fourfold
wider. With only 8 magnitudes available, spreading one scale over more values costs
noticeably more than it does with 8 exponent bits to absorb it.

## PTO vs ASC

The same difference as `per_token/04`, and it is structural rather than cosmetic.
ASC's `vdintlv` is a *pairwise* operation on two registers, so its loop is written
around producing two 64-lane halves and combining them. VMI's `vunzip` splits one
value, and the value is already 128 lanes, so the loop body has no pairing at all:

```
ASC per 128 values:  2 loads, 2 converts, 2 multiplies, vdintlv, vor, vmin,
                     reinterpret, convert, store
PTO per 128 values:  1 load, 1 convert, 1 multiply, vunzip, vor, vmin,
                     convert, store
```

The saving is the duplicated half of the value path — the same pattern as
[cast_back/05](../cast_back/05_fp4_e2m1.md), where ASC had to split 128 FP4 values
into two float32 registers and duplicate everything downstream.

Measured: 28 ASC operations against 26 — the only `per_block` variant where PTO
comes out ahead on the static count, and it is the one where ASC has a value path
to duplicate.

## SIMT — the hand-written encoder again, and the tile makes it cheaper

The FP4 output costs SIMT the same eighteen-line e2m1 encoder as
[per_token/04](../per_token/04_fp32_in_fp4_out.md), for the same reason: ASC and
PTO finish with a hardware `float32 -> e2m1` convert and only have to pre-round
to bfloat16 with a sticky bit, and no such convert is reachable from a `SimtVF`
region. The encoder is copied into this file rather than shared, so the file
stands alone.

What this variant's tile geometry *does* make easy is the pairing the page above
describes as natural. A thread takes one output byte and both its nibbles come
from the same row:

```python
for i, j in T.Parallel(bm, bk // 2):
    inv = inv_ub[0]
    lo = e2m1_nibble(T.Cast("float32", x_ub[i, 2 * j]) * inv)
    hi = e2m1_nibble(T.Cast("float32", x_ub[i, 2 * j + 1]) * inv)
    q_ub[i, j] = T.Cast("uint8", lo | (hi << 4))
```

The scale is one scalar for the whole tile, so there is no group arithmetic to get
wrong — which is exactly the accuracy interaction this page opens with, seen from
the thread side.

14 lines against ASC's 29 and PTO's 29, **plus** the eighteen excluded encoder
lines that `tools/vf_lines.py` does not count in any tier. Counting them, SIMT is
the longest of the three here, and that is the truthful summary.

## What the harness checks

- scales within 1 ULP;
- **the FP4 code budget**: `assert differing / total < 0.02` against the bit-exact
  torch packer. e2m1 has 8 magnitudes, so one differing code is a factor of up to
  1.5 — far too coarse for a value tolerance, which is why this counts codes
  instead.
