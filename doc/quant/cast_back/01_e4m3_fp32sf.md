# cast_back 01 — FP8 values, one FP32 scale per 32 channels, either output dtype

The first kernel in the ladder, and the one with the least arithmetic in it, so
that all the attention can go on *how the hardware is addressed*.

```
q  : (M, K)      float8_e4m3fn   quantized values
sf : (M, K/32)   float32         one scale per (token, 32-channel group)
out: (M, K)      bfloat16
```

$$
\mathrm{out}[m,k] = \mathrm{float}(q[m,k]) \cdot \mathrm{sf}\left[m, \left\lfloor k/32 \right\rfloor\right]
$$

Every value in a group of 32 is multiplied by the **same** scale. That is the whole
idea of block-wise quantization: $K/32$ scales instead of $K$, and the quantized
values get to use the full FP8 range within each group.

Why dequantize at all, when the quantized form is what the GEMM wants? Because a
later op — a norm, an activation — may need real magnitudes.

## Worked example

One token, $K = 64$, so two groups of 32:

| | value |
|---|---|
| `q[0, 0:4]` | `[112, 224, -448, 56]` |
| `sf[0, 0]` | `0.00892857`, i.e. $\frac{4}{448}$ |
| `out[0, 0:4]` | `[1.0, 2.0, -4.0, 0.5]` |

The FP8 codes are exact small integers here, which makes the arithmetic easy to
follow:

$$
112 \cdot \frac{4}{448} = 1 \qquad -448 \cdot \frac{4}{448} = -4
$$

`harness/doc_examples.py` re-checks that 448 is exactly representable in e4m3, so
the choice of 448 as the quantization target stays justified in the file rather
than only in prose.

## Torch

```python
grouped = q.float().view(m, k // group_size, group_size)
out = grouped * sf.unsqueeze(-1)
return out.view(m, k).to(torch.bfloat16)
```

Three lines. Everything below is the same three lines, written for a vector unit.

## ASC — the hardware model

### Four levels of memory, all explicit

```
Global Memory (GM)      the tensors the host sees
    | T.copy                       DMA, on the MTE2 engine
Unified Buffer (UB)     256 KB of on-chip SRAM, T.alloc_shared
    | S.vld                        vector load
Vector Register (VRF)   256 bytes each, the only thing compute can touch
    | S.vsts                       vector store
Unified Buffer
    | T.copy                       DMA out, on MTE3
Global Memory
```

`T.alloc_shared` is **Unified Buffer** here, not CUDA shared memory — the name is
inherited from the GPU backend and is a little misleading.

### Lanes: why the loop steps by 64

One register is 256 bytes. In float32 that is **64 lanes**, so compute proceeds 64
values at a time and a 128-wide row is two strips. That number drives every loop
bound in this repo, and it is the single most important thing to internalise about
this backend. See [lane widths](../../vf-lane-widths-and-limits.md).

### Distribution modes

An Ascend load or store is not just an address — it carries a `dist=` describing
how memory maps onto lanes. This kernel uses three:

| mode | what it does |
|---|---|
| `UNPK4_B8` | load 64 one-byte values, spread across 64 four-byte lanes, ready to convert |
| `BRC_B32` | load **one** float32 and broadcast it to all 64 lanes |
| `PK_B32` | on store, narrow each 32-bit lane to 16 bits and pack them — the bfloat16 output |

These are hardware capabilities, not DSL conveniences, which is why the kernel
never needs a separate broadcast or pack instruction.

### The awkward part: 32-wide groups in a 64-lane register

A scale covers 32 channels, but a register holds 64 float32 lanes — so one strip
spans **two** groups and needs two different scales. There is no 32-lane vector
type: the legal lane counts are `{1, 2, 4, 8, 64, 128, 256}` and 32 is absent.

The ASC answer is a predicate register and a select:

```python
mask_low = S.pset(32, "PAT_VL32")          # lanes 0-31 on, 32-63 off
lo = S.vld(sf_ub[group],     dist="BRC_B32")
hi = S.vld(sf_ub[group + 1], dist="BRC_B32")
scale = S.vsel(lo, hi, mask_low)           # mask ? lo : hi
```

Two broadcast loads and a select, to build one vector holding two scale values.

## The output dtype picks the store instruction

`compile_kernel` takes `out_dtype`, a Python string, so the branch below is taken
at **trace time** and only the chosen store is emitted. The same mechanism as
[per_token/06](../per_token/06_split_requant.md)'s `mode`. (It is *not* the same as
branching on a `T.unroll` loop variable, which silently takes the first arm — see
[known issues](../../known-issues.md).)

The arithmetic does not change. Only the store does, and the intuition is
inverted:

```python
if out_dtype == "bfloat16":
    S.vsts(out_ub[col], S.vcvt(scaled, T.bfloat16), dist="PK_B32")   # narrowing
else:
    S.vsts(out_ub[col], scaled, dist="NORM_B32")                     # plain
```

A register's lanes are already float32, so **writing float32 is the direct case** —
`NORM_B32` is a plain contiguous store, 64 lanes to 64 x 4 bytes. Writing bfloat16
is the one that needs work: 64 lanes of 32 bits must become 64 contiguous 16-bit
values, so `PK_B32` **packs as it writes**. The cheaper output dtype to emit is the
wider one.

### The float32 worked example

Same values as above, in a wider type:

| | value |
|---|---|
| `q[0, 0:4]` | `[112, 224, -448, 56]` |
| `out[0, 0:4]` | `[1.0, 2.0, -4.0, 0.5]` as float32, **exactly** |

FP8 e4m3 carries 3 mantissa bits, so a dequantized value needs only 4 significant
bits — bfloat16's 8 already cover it, and float32 buys no accuracy for the
quantized values themselves. It matters when the result feeds an accumulation that
would otherwise round repeatedly.

### Why this is a switch and not its own variant

As a standalone variant this was one changed line of arithmetic in each tier — the
whole file differed from this one by an output dtype. Carried as a switch, the two
store paths sit next to each other, which is where the lesson actually is: you can
read the narrowing store against the plain one without diffing two kernels.

## PTO vs ASC

### The store: ASC selects an instruction, VMI infers it

This is the clearest case in the kernel of VMI taking width from the buffer. ASC
picks the store *instruction* from the output dtype, so the two branches differ in
the distribution mode as well as the convert. VMI spells the store identically
either way, and only the convert appears or disappears:

```python
ASC, bfloat16 out:  S.vsts(out_ub[col], S.vcvt(v, T.bfloat16), dist="PK_B32")
ASC, float32  out:  S.vsts(out_ub[col], v,                     dist="NORM_B32")

PTO, bfloat16 out:  V.vstore(V.vcvt(v, "bfloat16"), out_ub[col])
PTO, float32  out:  V.vstore(v,                     out_ub[col])
```

The useful consequence: a kernel parameterised over its output dtype needs no
branch at all in PTO, while in ASC the mode has to be selected — which is exactly
what production's `store_out` helper does.

### The scale broadcast: three operations become one

VMI states the intent — "fill 64 lanes from consecutive scalars, in 2 segments" —
and lets the assembler pick the encoding:

```python
scale = V.vload(sf_ub[group], size=64, dist_mode="brc", group=2, stride=1)
```

One operation, no mask, and nothing in it is specific to the number 32. That
`group=` parameter is the single most useful idea in VMI: it makes **segmented**
behaviour a first-class argument on loads, stores, reduces and broadcasts alike,
rather than four unrelated hardware features.

### Conversions read like conversions

ASC spells a widening load as a distribution mode (`UNPK4_B8`, "unpack 4x from
bytes") and a narrowing store as another (`PK_B32`). You have to know the catalogue
to recognise that those mean "widen" and "narrow":

```python
raw = S.vld(q_ub[col], dist="UNPK4_B8");  values = S.vcvt(raw, T.float32)
S.vsts(out_ub[col], S.vcvt(scaled, T.bfloat16), dist="PK_B32")
```

VMI loads a vector and converts it, and the packing is implied by the destination
buffer's dtype:

```python
values = V.vcvt(V.vload(q_ub[col], size=64), "float32")
V.vstore(V.vcvt(scaled, "bfloat16"), out_ub[col])
```

This gap widens considerably in later variants — see [05](05_fp4_e2m1.md), where
ASC's FP8 store becomes four `part=` converts OR-ed together.

### Measured

`python tools/vf_lines.py` counts vector operations per variant: **9 for ASC
against 7 for PTO** here. (Both store branches are counted, which is why this is
one higher than a single-dtype kernel would be.) The saving is modest because this
variant has little machinery to collapse; [05](05_fp4_e2m1.md) is 16 against 8.

### Where PTO is not simpler

It is not torch. You still open `T.SimdVF()`, still place memory barriers by hand,
still live inside explicit UB buffers, and `size=` is mandatory on nearly every
call — so the token count per line sometimes goes *up* even as the operation count
goes down. "Torch-like vector operations inside an NPU schedule" is the fair
description.

## GPU vs NPU

The difference is the unit of work. `T.Parallel` names **one element** of an index
space and lets the compiler build the vectorisation. `T.SimdVF` names **one vector
register**, and you write the strip-mining, the lane arithmetic, the distribution
modes and the UB staging yourself. It is much closer to writing AVX-512 intrinsics
than to writing a CUDA kernel.

| | GPU | NPU |
|---|---|---|
| unit of work | one element `(i, j)` | one vector of 64 lanes |
| registers | `T.alloc_fragment` | `T.alloc_shared` (UB) then `S.vld` into VRF |
| shared memory | `T.alloc_shared` (SMEM) | the same call, different hardware |
| iteration | `T.Parallel(i, j)` | `T.serial` strip loop + 64-lane ops |
| vectorisation | implicit | explicit `dist=` on every load and store |
| scale indexing | `sf_shared[i // 32]` | `BRC_B32` load + mask + `vsel` |
| hazards | implicit for registers | `S.mem_bar` when UB is reused |

## What the harness checks

`harness/variants/cast_back.py`, variant `01`:

- builds `q` as `(randn * 100).to(float8_e4m3fn)` and `sf` as a positive
  `rand * 0.01 + 1e-4`, seeded, so the comparison is reproducible;
- compares against `oracle.cast_back(q, sf, (1, 32), out_dtype=bfloat16)` with
  **`atol=0.0`** — byte equality, not closeness. A dequantize is a multiply, so
  there is no reason for it to be approximate, and demanding exactness is what
  would catch a wrong distribution mode that still produced plausible numbers.
- the torch tier runs three shapes, `(32,128)`, `(8,64)` and `(64,256)`, to catch
  an implementation that only works when `K` is a multiple of 128.
