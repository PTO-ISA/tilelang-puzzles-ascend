# Torch tier — the prerequisite

Twenty-three exercises implementing the four quantization kernels in plain
PyTorch, on the CPU. They run in under a second each and need no simulator.

**Do these first** — a recommendation about learning, not a technical constraint.
Each exercise is the same arithmetic as its NPU counterpart with none of the
hardware: no lane widths, no distribution modes, no memory barriers. Getting the
algorithm wrong here costs a second; getting it wrong inside a vector kernel costs
thirty, and you will not know which of the two mistakes you made.

All three tiers are checked against `harness/oracle.py`, which is a standalone
PyTorch reference and imports nothing from `puzzles/`. So skipping this tier does
not stop an NPU variant from being verified — it just means learning the algorithm
and the vector surface at the same time. If you are unsure what a kernel is
*supposed* to compute, the answer is in the oracle and in these exercises, not in
the kernel.

## Working them

```bash
python -m harness.check torch/cast_back/01 --role puzzle   # fill in the TODO
python -m harness.check torch/cast_back/01                 # the reference
```

Each puzzle file is the answer file with the implementation removed and the hint
left in its place — same docstring, same function signature. The worked examples
live in the variant pages under `doc/quant/` and the checks live in `harness/`, so
a variant file is only ever the kernel. Puzzles are generated by
`tools/make_puzzles.py`, so they cannot drift apart.

An unsolved puzzle prints `TODO`, not a traceback.

## Explicit by design

These files import **constants** (`E4M3_MAX`, `CANONICAL_G`) but never math
helpers. Every bit operation is written out in plain torch, even where that means
repeating four lines in seven variants, because those operations *are* the
exercise. A reference answer reading

```python
exp_sf = ceil_log2_exp(amax / E4M3_MAX)      # not what this tier does
```

would teach nothing about the one idea the variant exists to convey. So it reads:

```python
bits = (amax / E4M3_MAX).view(torch.int32)
exp_sf = ((bits - 1) >> 23) + 1 - 127        # ceil(log2(v)) from the exponent
```

The separation of concerns across tiers follows from this:

| tier | teaches |
|---|---|
| torch | the quantization math — the floating-point and bit-level details |
| ASC / PTO | **instruction selection** for math you already know |

That is why an ASC kernel can be read as a translation rather than a derivation:
`S.vshrs(S.vsub(bits, one), 23)` is the line above, in hardware. The two FP4
codecs are the only helpers that recur as named functions, and even then the body
is explicit torch in the file — derived in `cast_back/06` (decode) and
`per_token/04` (encode), and copied verbatim into the later FP4 variants so those
solutions stay about their own config.

`harness/math_ops.py` keeps the same helpers for the *checking* side. That makes
the torch tier and the harness two independent implementations of the same
arithmetic, compared against each other on every run.

## The shared maths

All four kernels are these three lines with a different reduction shape:

```
amax = max(|x|) over a group
sf   = max(amax, clamp_min) / max_value        # optionally rounded up to 2^k
q    = cast(x * (1 / sf))
```

| kernel | group | scale array |
|---|---|---|
| `cast_back` | — (the scale is an *input*) | — |
| `per_token` | 32 channels of one token | `(M, K/32)` |
| `per_block` | a 32×32 tile | `(M/32, K/32)` |
| `per_channel` | one channel over 32 tokens | `(M/32, K)` |

`clamp_min` exists because an all-zero group would give `sf_inv = max/0 = Inf` and
then `0 * Inf = NaN`, and a packed exponent byte of `0x00` would be a NaN scale for
the downstream GEMM. Every test deliberately zeroes row 0 to exercise it.

## The variant ladder

Each kernel's variants add one config at a time, and the numbering matches across
all three tiers — `per_token/03` is the same feature in torch, ASC and PTO.

| # | config introduced |
|---|---|
| 01 | the core operation, raw float32 scale |
| 02 | `round_sf` — scale rounded up to a power of two |
| 03 | `use_packed_ue8m0` — the scale as one exponent byte |
| 04 | the dtype axis — float32 input, FP4 (e2m1) output |
| 05 | `use_tma_aligned_col_major_sf` — transposed scale layout |
| 06 | `sf_only` / `cast_only`, and requant (`with_sf`) |
| 07 | the bfloat16 compute path, everything composed |

`cast_back` has its own ordering (it consumes scales rather than producing them),
and `per_block` and `per_channel` reach the same endpoint in 5 and 4 steps because
several configs collapse on their layouts.

## Why bother with a torch tier at all

Because it makes the GPU-vs-NPU comparison concrete instead of rhetorical.

Several of these files are three lines long and their NPU counterparts are eighty.
`per_token/05` is one `.T`; the ASC version needs a lane-index vector and a gather.
`cast_back/02` is one `.to()` argument; the NPU version changes the store
instruction. Reading the pair tells you exactly which part of the kernel's
complexity is the algorithm (none of it) and which is the hardware (all of it).

A few variants are also where the *numerical* subtleties are easiest to see, and
the demos measure rather than assert them:

- `per_token/02` checks the ceil-log2 bit trick against `math.ceil(math.log2(v))`.
- `per_token/06` measures how far `cast_only` diverges from the fused path, and why
  `round_sf` makes it exactly zero.
- `per_block/01` shows that coarse blocking costs little relative precision but
  loses values to **underflow** — the usual "one outlier ruins the tile" argument
  applies to integer quantization, not to FP8.
- `per_block/03` shows FP4 widening the granularity gap about fourfold.
